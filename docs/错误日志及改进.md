# 错误日志及改进

记录 Fstack-DPDk 1.0.1（IPv6 + F-Stack 收端）联调与实现过程中遇到的关键错误、根因和改进方式。

---

## 1. 配置阶段：F-Stack 要求 `[port0]` 必须写 IPv4 四元组

**现象**
```
port0 if config error: no addr
```

**根因**
F-Stack `ff_check_config()` 在 `lib/ff_config.c` 中强制校验 `addr` / `netmask` / `broadcast` / `gateway` 四元组。1.0.1 计划只保留 `addr6`，但当前版本（含 INET6）仍要求 IPv4 字段存在。

**改进**
- `configs/config.dac.ini` 和 `config.fibre.ini` 的 `[port0]` 补回 IPv4 占位：
  ```ini
  addr=192.168.1.2
  netmask=255.255.255.0
  broadcast=192.168.1.255
  gateway=192.168.1.1
  addr6=1111:2222:1111:2222:1111:2222:1111:0002
  prefix_len=64
  ```
- 实际数据面仍走 `addr6`（IPv6），IPv4 仅用于通过 F-Stack 校验。

## 2. 脚本阶段：`run_recv.sh` 退出时找不到 `release_env.sh`

**现象**
```
bash: /home/dev/HMH--8007/Fstack-DPDk/scripts/release_env.sh --link dac: No such file or directory
```

**根因**
`run_recv.sh` 中把参数拼在了一个双引号里：
```bash
bash "${SCRIPT_DIR}/release_env.sh --link ${LINK_NAME}"
```
bash 会把整个字符串当成路径。

**改进**
改为正确写法：
```bash
bash "${SCRIPT_DIR}/release_env.sh" --link "${LINK_NAME}"
```

## 3. DPDK 环境：VFIO 组不 viable（IOMMU 同组含管理口）

**现象**
```
EAL: 0000:42:00.1 VFIO group is not viable! Not all devices in IOMMU group bound to VFIO or unbound
EAL: Bus (pci) probe failed.
No probed ethernet devices
```

**根因**
本机 82599 双口（`42:00.0` / `42:00.1`）与 PCIe 桥、igc 管理口同属 IOMMU group 11。`vfio-pci` 要求组内设备全部绑 vfio 或全部未绑，而管理口不能绑 vfio，因此仅绑 `42:00.1` 不够。

**改进**
- 收端 `setup_env.sh` / `release_env.sh` 改为绑定/释放 `uio_pci_generic`（可单口绑定，且受 DPDK 支持）。
- `f0` 和 `f1` 一并绑定/还回，避免残留 `ixgbe` 干扰 probe。
- `link_profile.sh` 增加 `LINK_SIBLING_IFACE` / `LINK_SIBLING_PCI` 描述同组口，并增加通用 DPDK 绑定/释放函数。

## 4. 参数解析：`--output` 等应用参数被忽略

**现象**
```
[*] Config: output=Test/udp_dpdk_output.bin, dst_port=8888, ...
```
明明传了 `--output test/output/live_dac.bin`，仍打印默认值。

**根因**
`split_argv_at_dd` 把 `--` 之后的参数传给 `parse_app_args`，但缺少 `argv[0]`。`getopt_long` 默认从 `argv[0]` 开始扫描，第一个长选项 `--output` 被跳过，因此没解析到。

**改进**
`parse_app_args` 手动构造一个带占位程序名的 `optv`：
```c
optv[0] = "fstack_udp_recv";
for (i = 0; i < argc; i++) optv[i + 1] = argv[i];
getopt_long(optc, optv, ...)
```

## 5. F-Stack IPv6 地址：DAD 导致地址不可用

**现象**
```
[!] ff_bind 1111:2222:1111:2222:1111:2222:1111:0002 failed, fallback [::]:8888 ok
[*] UDP socket ready [::]:8888
[*] RX progress: total_rx=0 matched=0
```

**根因**
F-Stack 把 `addr6` 配置为 `IN6_IFF_AUTOCONF`，默认会进入 **TENTATIVE** 状态做 Duplicate Address Detection（DAD）。FreeBSD 栈在地址未通过 DAD 前不会把匹配该目的地址的包交给 socket，表现为 `ff_bind` 失败或收不到包。

**改进**
在 `config.dac.ini` / `config.fibre.ini` 的 `[freebsd.sysctl]` 中禁用 DAD：
```ini
net.inet6.ip6.dad_count=0
```
`nd6_dad_start` 判断 `V_ip6_dad_count == 0` 会直接清除 `IN6_IFF_TENTATIVE`，地址立即可用。

## 6. F-Stack 栈溢出：`struct linux_sockaddr` 只有 16 字节

**现象**
收到首包后崩溃：
```
[*] First UDP datagram from F-Stack (1344 B payload)
*** stack smashing detected ***: terminated
```

**根因**
F-Stack `include/ff_api.h` 定义：
```c
struct linux_sockaddr {
    short sa_family;
    char  sa_data[14];
};
```
只有 16 字节。但 `ff_recvfrom` 对 IPv6 地址会调用 `freebsd2linux_sockaddr`，把 28 字节的 `sockaddr_in6` 写到 `linux_sockaddr`，溢出 12 字节，触发 canary 检测。

**改进**
`rx_loop` 中 `ff_recvfrom` 的 `from` 参数从 `struct linux_sockaddr` 改为 `struct sockaddr_storage`（128 字节），避免栈溢出。F-Stack 的转换函数会按实际长度写入，只要缓冲区足够大即可。

## 7. 退出阶段：F-Stack/DPDK teardown 触发 double free

**现象**
Ctrl+C 后：
```
free(): double free detected in tcache 2
```
统计块来不及输出。

**根因**
`run_recv_pipeline()` 内已经调用了 `fstack_udp_socket_close()` 和 `rx_channel_destroy()`，`main()` 返回后又重复调用一次。另外 F-Stack 的 `ff_stop_run()` 之后的全局清理也可能存在内部 double free。

**改进**
- 去掉 `main()` 中的重复 cleanup。
- 在 `run_recv_pipeline` 正常/信号退出路径，先打印统计和 `INCOMPLETE` 提示，然后直接 `_exit()` 跳过有问题的 F-Stack/DPDK teardown。
- `run_recv.sh` 的 `trap` 仍负责把网卡还回内核，所以不会漏掉网卡恢复。

## 8. payload 长度不匹配：发端 1352 B vs 收端期望 1344 B

**现象**
```
[!] payload data 1352 > cpbuf 1344; 增大 UDP_RXBUF_SLOT_SIZE
```

**根因**
发端 pcap 生成的 payload 为 8B 头 + 1344B 数据 = 1352B，但 `demo_udp_config.h` 中 `UDP_RX_PAYLOAD_SIZE` / `UDP_RXBUF_SLOT_SIZE` 定义为 1344B。`raw` 模式下期望整段 UDP payload 为 1344B。

**改进**
发端已修复为 8B 头 + 1336B 数据 = 1344B，与收端 `UDP_RX_PAYLOAD_SIZE` 对齐。若后续需要 raw 透传 1344B 数据，应统一调整 `SEND_PAYLOAD_SIZE` 和 `UDP_RX_PAYLOAD_SIZE`。

## 9. 发端自动释放网卡（已改进）

**现象**
`sender/run_pktgen_sender.sh` 运行结束后，f1 仍被 `vfio-pci` 占用；下一次 8007 启动收端时可能看到 `Link Down`，需要手动执行 `dpdk-devbind.py -b ixgbe 0000:42:00.1` 恢复。

**根因**
早期脚本没有注册 `trap`，pktgen 退出后不会主动还回网卡和恢复 IPv6；与 8004 上稳定 sender 的行为不一致。

**改进**
- 在 `sender/run_pktgen_sender.sh` 中增加 `release_sender_env()`：检测 PCI 当前驱动为 `vfio-pci` 时，调用 `dpdk-devbind.py -b ixgbe` 还回；随后通过 `test/internet/setup_f1_ipv6.sh` 恢复本机 IPv6。
- `run_send()` 中注册 `trap release_sender_env EXIT` 与 `trap on_send_interrupt INT TERM`，保证正常结束、Ctrl+C、SIGTERM 都会释放。
- 增加 `--no-release` 选项，供需要保留 DPDK 绑定做连续测试的场景。
- 同时把 `sender/include/sender_config.h` 的 `SEND_PAYLOAD_SIZE` 从 1344 改为 1336（数据区字节），使生成的 pcap 在 raw 模式下 UDP payload = 8B头 + 1336B体 = 1344B，与收端 `UDP_RX_PAYLOAD_SIZE` 一致。

## 10. 8007 做收端丢包率高于 8004（RX checksum · 已修复）

**现象**
相同硬件与 pcap 流下，**8007 作收端丢包明显高于 8004**。`tcpdump` 能看到包到网卡，但 `fstack_udp_recv` 的 `total_rx` 不足。

**根因（已确认）**
`F-stack/lib/ff_dpdk_if.c` 启用 `RTE_ETH_RX_OFFLOAD_CHECKSUM` 时，82599 常把合法 IPv6 UDP 标成 `RTE_MBUF_F_RX_L4_CKSUM_BAD`，`ff_veth_input` 直接丢弃。

**修复**
两端对齐：禁用 RX checksum offload（`#if 0` 或等价）；重编 `libfstack.a` + 收端二进制。

**验证**
修复后冒烟 / 1e5 可 COMPLETE，`total_rx` 可接近发包数。

**说明（勿与 §24 混淆）**
曾用加大 `cpbuf` 让 2e6@6G「收满」，但 **peak 飙到数万**，属饮鸩止渴。写盘路径 peak 打满见 §24。

## 12. 8004 做收端 total_rx=0：IOMMU Translated 模式拦截 DMA

**现象**
8004 做 DPDK 收端时，`tcpdump`（内核态）能看到包到达网卡，但 F-Stack / testpmd（DPDK 态）`total_rx=0` 或仅收极少数包。DPDK 网卡硬件计数器 `ipackets` 有值，但 `rte_eth_rx_burst` 返回 0。

**根因**
8004 内核无 `iommu=pt` 参数，IOMMU 默认为 **Translated（翻译）模式**。DPDK 使用 `igb_uio` / `uio_pci_generic` + PA（物理地址）模式做 DMA，但 Translated 模式下 IOMMU 拦截未映射的物理地址 DMA——82599 网卡在 MAC 层收到包（`ipackets` 递增），但 DMA 到 RX 描述符环失败（`rte_eth_rx_burst` 返回 0）。

对比 8007：内核有 `iommu=pt`，IOMMU 为 **identity（直通）模式**，PA 模式 DMA 直接通过。

**排查过程**
1. tcpdump 内核态抓包正常（100 包全到）→ 线路和 MAC/IP/端口无误
2. F-Stack pcap 0 字节 → DPDK 层未收到
3. testpmd rxonly 同样仅收极少数包 → 非 F-Stack 问题
4. DPDK 22.11 / 24.11 均复现 → 非版本回归
5. `igb_uio` / `uio_pci_generic` 均复现 → 非 UIO 驱动问题
6. per-queue 统计显示包在 queue 0 → 非 RSS 分队列问题
7. 对比 8007（收端正常）发现 `iommu=pt` 差异

**改进**
- `scripts/setup_env.sh` 增加 `ensure_iommu_identity()`：运行时将 IOMMU 组切换为 `identity`（直通），无需重启。
- `scripts/lib/link_profile.sh`：`DPDK_BIND_DRIVER` 改为 `igb_uio`（F-Stack DPDK 推荐）。
- 编译 `igb_uio.ko` 内核模块（DPDK `meson configure build -Denable_kmods=true && ninja -C build kernel/linux/igb_uio/igb_uio.ko`）。
- **永久修复**：在 `/etc/default/grub` 的 `GRUB_CMDLINE_LINUX` 添加 `iommu=pt`，`update-grub` + 重启。

**验证**
IOMMU identity 后，8007 pktgen 1000 包 → 8004 F-Stack 收到 940/1000（94%），输出文件 1.3MB。

## 13. F-Stack IPv6 UDP RX checksum offload 误判

**现象**
即使 IOMMU 修复后，部分 IPv6 UDP 包被 F-Stack `ff_veth_input` 在 checksum 检查处丢弃。

**根因**
82599 ixgbe DPDK 驱动对 IPv6 UDP 的 L4 checksum 标记可能误判为 BAD，F-Stack `ff_veth_input` 检测到 `RTE_MBUF_F_RX_L4_CKSUM_BAD` 后直接 `rte_pktmbuf_free` 丢弃。

**改进**
`F-stack/lib/ff_dpdk_if.c` 中禁用 RX checksum offload（`RTE_ETH_RX_OFFLOAD_CHECKSUM` 不再设置），避免硬件误判导致丢包。实际联调走 IPv6 纯 UDP 单流，软件栈不需要硬件 checksum 校验。

## 14. pktgen 无法加载 10000+ 包的大 pcap

**现象**
8007 pktgen 发送 1000-5000 包时 8004 收端正常（94-99%），但 10000+ 包时 8004 收到 0 包。tcpdump（内核态）确认 100000 包确实到达 8004 网卡。

**根因**
pktgen 的 `-s 0:pcap_file` 加载 pcap 时有内部缓冲限制。pcap 超过 ~5000 包（~7MB）时 pktgen 无法加载，静默失败——进程正常退出但未发送任何包。

**改进**
`sender/run_pktgen_sender.sh` 的 `PCAP_TEMPLATE_MAX` 从 100000 改为 **5000**。发送 >5000 包时，pcap 只生成 5000 包模板，pktgen 循环发送至目标 `--count`。

**验证**
- 5000 包 pcap + `--count 100000 --rate-mbps 6000` → 8004 收到 **99866/100000（99.87%）**，5.6 Gbps，129MB 输出。
- 1000 包：963/1000（96.3%）
- 2000 包：1949/2000（97.5%）
- 5000 包：4963/5000（99.3%）

## 15. pktgen 尾部截断导致「固定少量丢包」（与速率无关）

**现象**
收端 `Buffer drops=0`、`Ring full drops=0`，但 `matched` 总比 `--count` 少 7~130 个；丢包集中在 **尾部 seq**，低速（1Gbps）和高速（6Gbps）都会出现，看起来像收端问题。

**根因**
pktgen 用 5000 包 pcap 循环发送至 `--count` 时，`.pkt` 脚本里 `stop 0` + `quit` 过早结束，TX 队列未排空；pktgen 实际发送数略少于 `set 0 count N`。

**改进**（`sender/scripts/run_pktgen_replay.sh`）
1. 去掉 `stop 0`，仅靠 `set 0 count` 自动停发 + 加长 drain `sleep`
2. 发端自动加余量：`margin = count/1000 + 64`（上限 4096），收端仍用原始 `--count`
3. 支持 `uio_pci_generic` / `vfio-pci` / `igb_uio` 绑定检查
4. 8007 非交互：`NO_PROMPT=1`

**验证**（8007 发 → 8004 收，余量修复后）
| 包数 | 速率 | 结果 |
|------|------|------|
| 1e5 | 1Gbps | **COMPLETE** 100018/100000 |
| 1e5 | 6Gbps | **COMPLETE** 100001/100000 |
| **2e6** | **6Gbps** | **COMPLETE** 2000013/2000000，2.6GB，5.63 Gbps |

## 18. KNI 启动 SIGSEGV：`ff_kni_process` / virtio_user RX（2026-07-13）

**现象**
开启 `[kni] enable=1` 后，`ff_kni_alloc` 能创建 `virtio_user0`/`veth0`，但一进 `ff_run` 即在 `ff_kni_process` → `rte_eth_rx_burst(virtio)` **SIGSEGV**。  
强制 `--iova-mode=va` 后 PCI/`igb_uio` 报 `Expecting 'PA' IOVA mode ... not initializing`，物理口起不来。

**根因**
1. 用 `/usr/local/include` 重编的 `ff_dpdk_kni.o` 与进程链接的 **`F-stack/dpdk-install` DPDK** 的 `rte_eth_fp_ops` 布局不一致 → 读到 `rxq.data=NULL` 后解引用崩溃。  
2. `virtio_user` 的 `queue_size` 曾用 KNI ring 深度 2048，与 eth 队列 `RX_QUEUE_SIZE=512` 不一致（已改为 512）。  
3. 本机 **igb_uio 必须 PA**，不能全局改 VA。

**改进**
- `ff_dpdk_kni.c`：`queue_size=512`；TX 在 `nb_to_tx==0` 时跳过；RX/TX 前校验 `rte_eth_dev_is_valid_port` / `fp_ops`。  
- 重编 `ff_dpdk_kni.o` / `ff_config.o` 时 **-I$FF_PATH/dpdk-install/include 优先于 /usr/local**。  
- `config.dac.ini`：`[kni] method=reject udp_port=8888`；`numa_on=0`（避免 virtio 口误读 `port_cfgs`）。  
- `setup_kni_ops.sh` + `run_recv.sh --kni-ops`：给 `veth0` 配运维地址 `…:0004/64`。

## 19. 对端 ping6 Network unreachable（DAD 摘掉 :0002）

**现象**
8007 配上 `…:0002/64` 后为 `tentative`，随后全局地址消失，`ping6 …:0004` 报 `Network is unreachable`。

内核 IPv6 DAD 失败或未完成导致地址被移除；同网段无其它全局源地址时无法路由到 `:0004`。

```bash
ping6 -c 3 -W 1 -I enp66s0f1 1111:2222:1111:2222:1111:2222:1111:0004
```
**验证：** 3/3 通，rtt ~0.14ms（2026-07-13）。

## 21. TCP 握手后数据面停滞（仅收前几十帧）

**现象（V2.0 联调）**
内核 TCP 客户端 `connect` 成功，但随后 `cwnd` 塌到 1、`RTO` 飙到数十秒；收端 matched 停在约 20 帧，`stream_buf` 残留半帧。

**根因**
`config.dac.ini` 默认开启 TX TCP checksum offload（82599）。F-Stack 回的 ACK 在链路上校验失败，对端认为丢包并指数退避。

**改进**
```ini
tx_csum_offoad_skip=1
```
并保证 `[kni] tcp_port=8888`（业务 TCP 留 F-Stack，不进 KNI）。

**验证：** 100/100、1e5、1e6 帧 COMPLETE；见 `docs/性能统计.md` V2.0。

## 22. F-Stack 多进程 TCP 客户端握手不稳定（V2.2）

**现象**
`run_tcp_fstack_send_mp.sh`（primary + secondary，每进程一连接）时，多数 worker `connect timeout`；偶发仅 1～2 条连接成功。成功单流仍可达 ~3.6 Gbps（traffic-only）。

**判断**
F-Stack 多进程各绑独立 RX/TX 队列；TCP 客户端的 SYN-ACK 经 RSS 可能落到非 PCB 所在进程。服务端 SO_REUSEPORT 场景有成熟路径，**出站客户端**跨进程分发在本环境（IPv6 + 82599）未稳定。

**已尝试（未根治）**
- 串行/并行启动、固定 src_port、`symmetric_rss`、primary linger、idle-primary 只保活

**建议**
- 正式测吞吐：单进程 `fstack_tcp_send`，或内核多进程 `tcp_stream_send`
- 若必须 F-Stack 多核发：专项查跨进程 TCP 包分发 / flow director，再开性能基线

**相关：** `scripts/run_tcp_fstack_send_mp.sh`；收端 `--traffic-only --max-conns`；`docs/性能统计.md` V2.2。

## 23. UDP 减栈成本：ZC 无效、半旁路有效（2026-07-13）

**背景：** 发端只能单五元组（不能 RSS）；栈路径 UDP 墙约 6G。

| 手段 | 做法 | 1e6 结果 |
|------|------|----------|
| `--zc-recv` | 仍过 sockbuf，少一次 uiomove | 6G 下 +~12 Mbps，可忽略 |
| `--udp-bypass` | `ff_regist_packet_dispatcher` + IPv6/UDP 解析（对齐 UDP_DPDK） | 9G 下栈路径 INCOMPLETE ~5.8G；旁路 COMPLETE **~8.5G** |

**要点：** 半旁路仍跑在 F-Stack 进程内（EAL/`ff_run`），ND/其它口流量可回栈；业务 UDP 不再建 socket。与 `--zc-recv` 互斥。线速 1e6 COMPLETE **~9.4G**，bufpool peak ~12%。详见 [性能统计.md](./性能统计.md) V1.1。

## 24. 8007 作收端：O_DIRECT 写盘 CQE 阻塞导致 peak 打满（2026-07-09）

**对照**
8004 收、`cpbuf=16384`：2e6@6G COMPLETE，peak ≈163。  
8007 同配置：peak 打满 16384 + 大量 Buffer drops。

**关键诊断：`--discard`**
writer 只出环还池、不写盘 → COMPLETE、peak=**11** → **RX/F-Stack 足够**；高 peak 来自 writer 在 `udp_writer_submit`→`acquire_buf_slot` **阻塞等 CQE** 时 RX 继续入环。

**结论**
根因是 **8007 本机 NVMe + O_DIRECT 的 io_uring 完成延迟**（内核 6.8、managed IRQ 等），不是协议栈。加大 cpbuf 只是掩盖，不作长期方案。数据见 [性能统计.md](./性能统计.md)「8007 作收端」。
