# 错误日志及改进

记录 Fstack-DPDk 1.0.1（IPv6 + F-Stack 收端）联调与实现过程中遇到的关键错误、根因和改进方式。

---

## 1. 配置阶段：F-Stack 要求 `[port0]` 必须写 IPv4 四元组

**现象**
```
port0 if config error: no addr
```

**根因**
F-Stack `ff_check_config()` 在 `lib/ff_config.c` 中强制校验 `addr` / `netmask` / `broadcast` / `gateway` 四元组。1.0.1 计划只保留 `addr6`，但当前版本（含 INET6）仍要求 IPv4 字段存在。

**改进**
- `configs/config.dac.ini` 和 `config.fibre.ini` 的 `[port0]` 补回 IPv4 占位：
  ```ini
  addr=192.168.1.2
  netmask=255.255.255.0
  broadcast=192.168.1.255
  gateway=192.168.1.1
  addr6=1111:2222:1111:2222:1111:2222:1111:0002
  prefix_len=64
  ```
- 实际数据面仍走 `addr6`（IPv6），IPv4 仅用于通过 F-Stack 校验。

## 2. 脚本阶段：`run_recv.sh` 退出时找不到 `release_env.sh`

**现象**
```
bash: /home/dev/HMH--8007/Fstack-DPDk/scripts/release_env.sh --link dac: No such file or directory
```

**根因**
`run_recv.sh` 中把参数拼在了一个双引号里：
```bash
bash "${SCRIPT_DIR}/release_env.sh --link ${LINK_NAME}"
```
bash 会把整个字符串当成路径。

**改进**
改为正确写法：
```bash
bash "${SCRIPT_DIR}/release_env.sh" --link "${LINK_NAME}"
```

---

## 3. DPDK 环境：VFIO 组不 viable（IOMMU 同组含管理口）

**现象**
```
EAL: 0000:42:00.1 VFIO group is not viable! Not all devices in IOMMU group bound to VFIO or unbound
EAL: Bus (pci) probe failed.
No probed ethernet devices
```

**根因**
本机 82599 双口（`42:00.0` / `42:00.1`）与 PCIe 桥、igc 管理口同属 IOMMU group 11。`vfio-pci` 要求组内设备全部绑 vfio 或全部未绑，而管理口不能绑 vfio，因此仅绑 `42:00.1` 不够。

**改进**
- 收端 `setup_env.sh` / `release_env.sh` 改为绑定/释放 `uio_pci_generic`（可单口绑定，且受 DPDK 支持）。
- `f0` 和 `f1` 一并绑定/还回，避免残留 `ixgbe` 干扰 probe。
- `link_profile.sh` 增加 `LINK_SIBLING_IFACE` / `LINK_SIBLING_PCI` 描述同组口，并增加通用 DPDK 绑定/释放函数。

## 4. 参数解析：`--output` 等应用参数被忽略

**现象**
```
[*] Config: output=Test/udp_dpdk_output.bin, dst_port=8888, ...
```
明明传了 `--output test/output/live_dac.bin`，仍打印默认值。

**根因**
`split_argv_at_dd` 把 `--` 之后的参数传给 `parse_app_args`，但缺少 `argv[0]`。`getopt_long` 默认从 `argv[0]` 开始扫描，第一个长选项 `--output` 被跳过，因此没解析到。

**改进**
`parse_app_args` 手动构造一个带占位程序名的 `optv`：
```c
optv[0] = "fstack_udp_recv";
for (i = 0; i < argc; i++) optv[i + 1] = argv[i];
getopt_long(optc, optv, ...)
```

## 5. F-Stack IPv6 地址：DAD 导致地址不可用

**现象**
```
[!] ff_bind 1111:2222:1111:2222:1111:2222:1111:0002 failed, fallback [::]:8888 ok
[*] UDP socket ready [::]:8888
[*] RX progress: total_rx=0 matched=0
```

**根因**
F-Stack 把 `addr6` 配置为 `IN6_IFF_AUTOCONF`，默认会进入 **TENTATIVE** 状态做 Duplicate Address Detection（DAD）。FreeBSD 栈在地址未通过 DAD 前不会把匹配该目的地址的包交给 socket，表现为 `ff_bind` 失败或收不到包。

**改进**
在 `config.dac.ini` / `config.fibre.ini` 的 `[freebsd.sysctl]` 中禁用 DAD：
```ini
net.inet6.ip6.dad_count=0
```
`nd6_dad_start` 判断 `V_ip6_dad_count == 0` 会直接清除 `IN6_IFF_TENTATIVE`，地址立即可用。

## 6. F-Stack 栈溢出：`struct linux_sockaddr` 只有 16 字节

**现象**
收到首包后崩溃：
```
[*] First UDP datagram from F-Stack (1344 B payload)
*** stack smashing detected ***: terminated
```

**根因**
F-Stack `include/ff_api.h` 定义：
```c
struct linux_sockaddr {
    short sa_family;
    char  sa_data[14];
};
```
只有 16 字节。但 `ff_recvfrom` 对 IPv6 地址会调用 `freebsd2linux_sockaddr`，把 28 字节的 `sockaddr_in6` 写到 `linux_sockaddr`，溢出 12 字节，触发 canary 检测。

**改进**
`rx_loop` 中 `ff_recvfrom` 的 `from` 参数从 `struct linux_sockaddr` 改为 `struct sockaddr_storage`（128 字节），避免栈溢出。F-Stack 的转换函数会按实际长度写入，只要缓冲区足够大即可。

## 7. 退出阶段：F-Stack/DPDK teardown 触发 double free

**现象**
Ctrl+C 后：
```
free(): double free detected in tcache 2
```
统计块来不及输出。

**根因**
`run_recv_pipeline()` 内已经调用了 `fstack_udp_socket_close()` 和 `rx_channel_destroy()`，`main()` 返回后又重复调用一次。另外 F-Stack 的 `ff_stop_run()` 之后的全局清理也可能存在内部 double free。

**改进**
- 去掉 `main()` 中的重复 cleanup。
- 在 `run_recv_pipeline` 正常/信号退出路径，先打印统计和 `INCOMPLETE` 提示，然后直接 `_exit()` 跳过有问题的 F-Stack/DPDK teardown。
- `run_recv.sh` 的 `trap` 仍负责把网卡还回内核，所以不会漏掉网卡恢复。

## 8. payload 长度不匹配：发端 1352 B vs 收端期望 1344 B

**现象**
```
[!] payload data 1352 > cpbuf 1344; 增大 UDP_RXBUF_SLOT_SIZE
```

**根因**
发端 pcap 生成的 payload 为 8B 头 + 1344B 数据 = 1352B，但 `demo_udp_config.h` 中 `UDP_RX_PAYLOAD_SIZE` / `UDP_RXBUF_SLOT_SIZE` 定义为 1344B。`raw` 模式下期望整段 UDP payload 为 1344B。

**改进**
发端已修复为 8B 头 + 1336B 数据 = 1344B，与收端 `UDP_RX_PAYLOAD_SIZE` 对齐。若后续需要 raw 透传 1344B 数据，应统一调整 `SEND_PAYLOAD_SIZE` 和 `UDP_RX_PAYLOAD_SIZE`。

## 9. 发端自动释放网卡（已改进）

**现象**
`sender/run_pktgen_sender.sh` 运行结束后，f1 仍被 `vfio-pci` 占用；下一次 8007 启动收端时可能看到 `Link Down`，需要手动执行 `dpdk-devbind.py -b ixgbe 0000:42:00.1` 恢复。

**根因**
早期脚本没有注册 `trap`，pktgen 退出后不会主动还回网卡和恢复 IPv6；与 8004 上稳定 sender 的行为不一致。

**改进**
- 在 `sender/run_pktgen_sender.sh` 中增加 `release_sender_env()`：检测 PCI 当前驱动为 `vfio-pci` 时，调用 `dpdk-devbind.py -b ixgbe` 还回；随后通过 `test/internet/setup_f1_ipv6.sh` 恢复本机 IPv6。
- `run_send()` 中注册 `trap release_sender_env EXIT` 与 `trap on_send_interrupt INT TERM`，保证正常结束、Ctrl+C、SIGTERM 都会释放。
- 增加 `--no-release` 选项，供需要保留 DPDK 绑定做连续测试的场景。
- 同时把 `sender/include/sender_config.h` 的 `SEND_PAYLOAD_SIZE` 从 1344 改为 1336（数据区字节），使生成的 pcap 在 raw 模式下 UDP payload = 8B头 + 1336B体 = 1344B，与收端 `UDP_RX_PAYLOAD_SIZE` 一致。

## 10. 已知现象：8007 做收端丢包率高于 8004 做收端

**现象**
在相同硬件、相同 DPDK 绑定（vfio-pci / uio_pci_generic）和相同 pcap 流条件下，**8007 作为收端时丢包率明显更高**，而 **8004 作为收端时几乎不丢包**。该现象在之前的 DPDK 测试中也出现过。

**观察**
- 8007 做收端时，`tcpdump` 能看到包到达网卡，但 `fstack_udp_recv` 实际收到的包数不足（例如 100,000 包中差 5 包左右，且高速时差距更大）。
- 8004 做收端时，同样配置下能收满全部包。
- 已排除：pcap payload 长度不匹配（已统一为 1344B UDP payload）、F-Stack DAD（已禁用）、socket 地址溢出（已修复）、F-Stack teardown double free（已绕过）。

**可能原因（待进一步验证）**
1. **网卡 / 驱动差异**：8007 与 8004 虽然同为 82599 双口网卡，但 BIOS/IOMMU 分组、PCIe 插槽、固件版本或中断配置可能不同，导致 8007 上 DPDK 收包路径有微丢包。
2. **IOMMU 组影响**：8007 的 `42:00.0` / `42:00.1` 与 PCIe 桥、igc 管理口同处一个 IOMMU group，即使改用 `uio_pci_generic` 单口绑定，组内其他设备仍可能对 DMA 或中断路由产生干扰。
3. **DPDK 端口 / 队列配置**：`fstack_udp_recv` 当前使用 F-Stack 默认的单口单队列配置，未针对 8007 做接收描述符、RSS、burst 大小等调优。
4. **F-Stack 内部丢包**：F-Stack 的 IP/UDP 层在 IPv6 校验、分片、DAD 等环节仍可能丢弃少量包，需进一步抓 mbuf 或启用 F-Stack 统计定位。

**下一步排查建议**
- 8007 发 / 8004 收测试：用 `sender/run_pktgen_sender.sh --to-8004` 观察 8007 作为发端是否正常，8004 作为收端是否仍不丢包。
- 在 8007 收端启用 F-Stack / DPDK 统计：查看 `rx_missed_errors`、`rx_errors`、`imissed` 等计数，确认丢包发生在 NIC 还是 F-Stack 协议栈。
- 对比 8007 与 8004 的 `lspci -vv`、IOMMU group、`/proc/interrupts`、网卡固件版本。
- 必要时在 8007 上直接跑原生 DPDK `l2fwd`/`testpmd` 做收包基线，排除 F-Stack 因素。
